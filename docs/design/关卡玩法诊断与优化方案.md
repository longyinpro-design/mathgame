# 森林十八关 · 玩法诊断与优化方案

日期：2026-09-22 · 范围：森林岛 FL01–FL18 的**玩法层**（机制、决策空间、反馈、提示）
不在范围：学习闭环的命名与迁移（见《数学学习闭环优化方案》）、集市 MK01–MK18、美术与剧情

---

## 一、结论

谜题质量在上游，问题在谜题之外。

十八个机制没有一个是凑数的：FL06「只能试一次」、FL09「先预测再揭示」、FL11「贪心必败」这类设计放在商业解谜里也站得住。真正的病灶有三处，而且是同一个方向上的：

1. **十八关里只有五关的规则真的要求「先想」**。其余十三关的最省力解法是「试到对」。
2. **有六处设计好的「证明环节」在界面上没有入口**，所以设计文档里要求的解题证据从来没有产生过。
3. **第 3 档提示按当前局面实时报出下一步或答案**，而且可以无限次按——它把上面两件事同时抹平了。

第 3 条本轮已改（提示分层，见第五节）。前两条是这份方案的主体。

## 三、发现一：只有五关要求「先想」

把「试」的代价列出来，答案立刻就清楚了：

| 关 | 限制是什么 | 拿掉了限制会怎样 |
|---|---|---|
| FL06 | 只能投送一次 | 试三次就能区分三台机器，信息论那一层消失 |
| FL08 | 必须填每层袋应有的条数 | 不看条数就发现不了缺失的那条路线 |
| FL09 | 四处预测填满才揭示结果 | 直接看四个数字挑最大，比较变成了扫描 |
| FL10 | 必须选一个理由 | 凑出两条不碰面的路就算了，抽屉原理那一层消失 |
| FL18 | 试探消耗种子 | 无限试探，资源预留那一层消失 |

共同点：**「试」要么只有一次，要么花资源，要么必须先把预测写下来。**

而其余十三关，「试」是免费、无限、而且通常比想更快的：FL04 试四个数、FL05 试二十种排列、FL16 扫五种宽度、FL12 输了就撤销重来。

这里要说句公道话：**「试到对」本身不是坏玩法**。FL12 就是靠试归纳出「留 4 的倍数」，孩子从三次失败里学到的东西是真的。坏的是另一种情况——**当试比想更快时，孩子学到的是搜索，不是推理**。而这刚好是十三关。

## 四、发现二：六处「证明环节」没有入口

规则层定义了一批动作，界面层没有对应按钮，`complete()` 也不校验它们：

| 动作 | 在哪一关 | 设计文档里它要干什么 | 现状 |
|---|---|---|---|
| `band` | FL04 | 用三条光带标出每架灯被重复计了两次 | 无入口 |
| `total` | FL04 | 组成总量 47（=94÷2） | 无入口 |
| `classify` | FL14 | 把 8/9/10 分别归到可达或不可达 | 无入口 |
| `loss` | FL14 | 填「反转一步让终点少多少」 | 无入口 |
| `outcome_count` | FL15 | 数一次天平最多有几种结果 | 无入口 |
| `area` | FL16 | 解释宽加一格为什么可用长减两格 | 无入口 |

证据（在界面层检索这些动作名，无任何匹配）：

```
$ grep -rn 'kind":"band\|kind":"total\|kind":"classify\|kind":"loss\|kind":"outcome_count\|kind":"area"' scripts/ui/
（无输出）
```

后果不是「少做了几个操作」，而是：**`thinking_contract.required_evidence` 是空头支票。**

- FL04 要求「用三条光带标出每架重复计数两次，组成总量 47」——游戏里没有光带。
- FL14 要求「分类 8/9/10 并构造可达轨迹」——游戏里只能填两条路线。
- FL16 要求「解释宽增加一格为什么可用长减少两格」——游戏里没有这个输入。

这些恰好是数学里最有价值的那一半：**答案之外的论证**。现在这一半在游戏里不存在，只在设计文档里存在。

一处值得注意的对比：FL04 的 `complete()` 会检查「三对合称都称过」，说明作者是知道要给关键步骤加门禁的；漏掉的是那六个动作整批没接上界面，不是某一关忘了。

## 五、发现三：第 3 档提示是免费无限的答案播报（本轮已改）

改之前，`highest_hint` 封在 3，而第 3 档的内容由当前状态**实时重算**。两条合起来：**连按 H 就是一份不限次数的逐步答案播报。**

改前逐关第 3 档的原文：

| 关 | 改前第 3 档说的 |
|---|---|
| FL04 | 「把甲灯架调成 12，再对照它参与的两条合重。」 |
| FL16 | 「全部宽度里 3×6=18 格最大，点它来围定。」 |
| FL12 | 「当前取 2 颗，可以把 4 的整组留给守门人。」 |
| FL11 | 「撤销重来：有一趟要两件拼着走，小岚的独趟要用 5 号石。」 |
| FL17 | 「当前用 2 枚符，从 B 移到 C，能继续接住后手。」 |
| FL15 | 「在『若左重』分支，把 4 号放在右盘。」 |

这跟每一关自己的设计文档**直接冲突**。每关的 `thinking_contract` 里都有一条 `shortcut_to_check`，写的是「这条捷径必须被挡住」：

- FL16 写着「五种宽度全部试齐并围定真正最大的 3×6 才算完成」——而提示直接把 3×6 说了。
- FL04 写着「逐架试数在两位数合重下代价远高于先求总量」——而提示连试都不用试了。

### 本轮改动

提示拆成四档，原来那一档降级为第 4 档：

| 档 | 内容 | 例（FL16） |
|---|---|---|
| 1 | 问看哪里 | 「哪一条边已经由墙提供？」 |
| 2 | 说用哪条关系 | 「把一份木料给宽，两条宽边都要增加。」 |
| 3 | **指出关系，不给结论** | 「五种宽度都在下面了。木料总数不变——宽多分一点，长就少分一点，哪个乘积最大？」 |
| 4 | 带路（原第 3 档） | 「宽多的代价填 2：两条宽边各多占一格木料，长就少这么多。」 |

第 3 档的力度在后来的 P0/P1 改动里又收紧了一次：`total`／`length_loss` 这类要玩家亲手填的结论，
第 3 档一律不报数值，只在第 4 档报（见第十节）。

涉及的改动：

- `scripts/mechanisms/current_hint.gd`：新增 `guide()` 及逐家族的方向性提示。
- `scripts/mechanisms/mechanism_rules.gd`：档位改路由（1–2 取关卡文案，3 走 `guide`，4 走原来的 `next`）。
- `scripts/core/game_session.gd`：档位上限 3 → 4（读档校验同步放宽，旧档 `highest_hint ≤ 3` 仍然合法）。
- `tests/forest/hint_layers_test.gd`（新增 110 条）：四档都要有内容；第 3 档不等于第 4 档；逐关禁止原来那句答案的特征字串；第 3 档要随盘面变化；第 4 档兜底仍在。
- 两处既有断言跟着更新（它们原本钉的是「档位封在 3」这个旧行为）。

**底线没有动**：兜底还在。第 4 档仍然一步一报，只是要先经过前三档。所以「求助免费、失败不降奖励」这条立场没被推翻——改的是「求助的默认结果是思考题，不是答案」。

## 六、优化方案

### P0 · 让「试」有一次性的地方

| 项 | 改什么 | 为什么 | 风险 |
|---|---|---|---|
| P0-1 ✅ | 提示分层（已完成） | 见第五节 | 低 |
| P0-2 ✅ | FL05 的押注从「可选」改成必填；FL16 增加「先猜哪一份最大」 | 两关都有现成的目标量（FL05 的 `prediction`、FL16 的最大面积），现在却允许空着直接提交 | 低。FL05 的 `predict` 动作已存在，只改提交门禁 |
| P0-3 ✅ | FL04 接上 `total` 入口 | 「三次合重是两套灯架」这条主洞察现在只能从提示里听到，不能在棋盘上做出来 | 中。要动 UI 与 `complete()`，得做存档兼容（参照 FL16 `sweep` 标记的旧档分支写法） |

P0-2 是**已经有验证过的模板**：FL09 就是「先猜 → 四处预测填满 → 才揭示」，跑通了，把孩子从扫描逼回了预测。

实施记录见第十节。

### P1 · 补上或删掉那六处「证明环节」

| 项 | 改什么 | 说明 |
|---|---|---|
| P1-1 ✅ | FL14 接上 `classify` 与 `loss` | 这关现在处境最尴尬：侧板把「从 X 再走 N 步只能走到 2、6、10」算好了印在屏幕上，而设计要求的「分类 8/9/10」没有入口。**要么补入口，要么把这两条从 `required_evidence` 里删掉**——不能既写着要求又不给入口 |
| P1-2 ✅ | FL15 的「会分不开的：第 X 颗、第 Y 颗」改成提交后才显示 | 现在是一个实时求解器，玩家只需反复调直到提示消失 |
| P1-3 | 支线关难度校准 | FL13/14/15/16 挂在 FL01/06/08/10 之后，本该是变式挑战，实际比主线浅。FL13（同 FL01 参数加一条约束）方向是对的，FL14/15/16 不是 |

P1-1／P1-2 的实施与遗留见第十节；P1-3 仍需要试玩数据。

### P2 · 结构性

| 项 | 改什么 |
|---|---|
| P2-1 | 难度按认知类型重排，而不是按剧情排。现在 FL06（信息论直觉）夹在 FL05（排列）与 FL07（算术技巧）之间，认知跨度明显 |
| P2-2 | 给 `thinking_contract` 加一份实现对照表，把 `required_evidence` 逐条对上界面动作。不建这张表，第四节的缺口还会再长出来 |

## 七、不做什么

- **不动关卡参数与 `expected`。** 问题不在数值：FL04 的 29/35/30 是好参数，FL16 的 3×6=18 也是。动参数会牵动存档兼容、契约与全部验算，收益还不明确。
- **不动「提示免费、失败不降奖励」。** 那是明确的设计立场（README 有写），而且对三年级是对的：求助不该被罚。我给的是**求助分层**，不是求助收费。
- **不在没有试玩数据前重排关卡顺序。** P2-1 需要真实通过时间做依据，现在只有推断。

## 九、待确认

**单局时长我没有实测数据。** 上面所有关于「试比想更快」的判断，是按操作次数估的（FL05 二十次点击 vs 一次推理），不是按真实耗时。如果实测发现孩子在一关里会停留很久、根本不会去穷举，那 P0-2 的优先级要往下调，第三节的结论也要重写。

## 十、本轮实现（P0-2 / P0-3 / P1-1 / P1-2）

### 统一做法：入口拒绝 + `complete()` 校验 + `fresh()` 标记保旧档

同一份代码，两套判据，靠 `fresh()` 里新加的一个键区分：

| 存档 | 键 | 判据 |
|---|---|---|
| 这一版之后新建的 | 有（`proof` / `guessed`，与 FL16 原有的 `sweep` 同型） | 严格：证据没做出来就不算完成 |
| 加标记之前留下的 | 没有 | 沿用原判据，不会被判成无效 |

不用「字段有没有被填过」当判据，是因为这些字段（`total`／`prediction`／`classifications`／`length_loss`）在 `fresh()` 里一直存在，
默认值 0 与「没做过」无法区分；靠键的有无才分得开。

### 逐关改动

| 关 | 新入口 | 拒绝时机 | 完成判据 |
|---|---|---|---|
| FL04 | 盘面加「一套灯架的总重」输入（`total_expected` = 三合重之和 ÷ 2 = 47） | 没摆对就不放行「点亮村灯」 | 三对吻合 ＋ `weighed` 齐 ＋ 总重 = 47 |
| FL05 | 押注从「（可选）」改成「必填」 | 没押注就不放行「启动机器」 | 押注发生且押的数 = 这台机器在新输入上的输出（6×3+2 = 20） |
| FL14 | 盘面加 8／9／10 各判一格 ＋ 「宽…改一次向少几格」输入 | 没判因／代价算错就不放行「上路试试」 | 判因 = `[2,1,0]`（由可达枚举与奇偶两条约束推出，不是写死的）＋ 代价 = 4 |
| FL15 | 无（改的是显示） | —— | 不变 |
| FL16 | 盘面加「先押一注：最大能围出多少格」＋「宽多 1 格，长会少」输入 | 没押注就不放行调宽度；没算清代价就不放行「就围这份」 | 五种宽度扫齐 ＋ 围定最大值 ＋ 押注已发生 ＋ 代价 = 2 |

判因与代价都是**推出来的**，不是查表：`reason_for()` 先枚举五步内所有落点（`endings()`），落不到且奇偶不符判 1，落不到但奇偶相同判 2；
`flip_gap()` 取 ±2 的整个跨度；`WIDTH_STEP_LOSS = 2` 出自「三边用料是 2×宽＋长」这条规则本身。

FL15 的判定行从绘制里拆成了 `coin_verdict()`：提交前只说任务，提交后才批改「哪几颗分不开」。
拆成纯函数是为了让门禁能直接验行为——内联在绘制里的话，只有实机截图能证明它没泄漏。

### 验收（无头，可复现）

```

python3 tests/forest/run_checks.py --output /tmp/pixel-run/verification.json
```

候选 `ea05d77` ＋ 本轮工作树改动；15 个无头套件全绿，2573 条断言：

|---|---|

| `hint_layers_test.gd` | 110/110 |
| `assets_test.gd` | 1031/1031（新加的中文全部有字形） |
| 其余 12 个（boundary / session / story / p3–p8 / review_repairs / migration / discovery / route_redesign / twenty_four） | 全绿 |

端到端另有一层：`scenarios.gd` 的 18 关脚本已按新门禁补齐，`story_test`／`session_test`／`boundary_test`／`review_repairs_test` 都是通过它走完整条主线的，
所以「四关能不能真的结算」不是只靠规则层单测。

**记录与代码的绑定**：验收记录里带 276 个源文件的 `source_sha256`，逐个重算后 276/276 一致，
且 `source_stable_during_run: true`——即这份绿是在这一份代码上跑出来的，不是上一次的残留。
记录落在 `/tmp`（`/tmp` 会被系统清理），要复现就重跑上面那条命令；单条命令约 17 秒。

### 这一轮**没有**验证到的

1. **所有新增控件的实际版面没有肉眼看过。** 位置是按矩形算的（逐个与同屏其它元素核对过不重叠、不超过工作台纸面太多），
   没有跑窗口测试，所以不知道会不会挤、会不会被压住。要实机结论必须跑 `run_checks.py --windows`（会弹真实窗口）。
2. **仓内的验收记录 `docs/playtest/forest-release/verification.json` 不对应本轮代码。** 它在改动之前就已经是未提交状态；
   本轮的无头结果写在了 `/tmp`，没有覆盖它——覆盖会让它丢掉原来那份含窗口测试的记录，但保留又会让人以为它还是有效的。
   两难没有暗中处理，交给你定：要么跑一次完整套件重新生成，要么先把它恢复成 HEAD 版本。
3. **FL15 的提示第 3 档仍会在被请求时给出「这样安排九颗都能分开」的判定。** 那是玩家主动按 H 换来的、且属于「指关系」，
   与本轮要挡的「不花钱的实时求解器」不是一回事，但没有实测数据能证明孩子不会把它当免费答案用。

### 还剩的一处空洞

`thinking_contract` 里还差一条没有入口：**FL15 的 `outcome_count`**（「用一次至多 3 种结果说明一次不能区分 9 种情况」）。
`coin_rules` 的 `outcome_count` 字段与动作都在，但盘面没入口、`complete()` 也不校验。

我**没有**顺手把它接上，理由是它的设计价值存疑：问「一次天平最多有几种结果」只要求报 3，
而这条证据真正要说的是「3 < 9，所以一次不够」——门槛填一个 3 更像仪式，不像思考。
建议二选一：把它改写成「3×3 与 9 的关系」再给入口，或从 `required_evidence` 里删掉。
另外 FL04 的 `band`（六格光带）我判定为**不可校验的装饰**：规则对它的取值只有 `-1..1` 的约束，
没有任何一种摆放是「对的」，所以它接不上完成判据——要么改成有唯一解的标注玩法，要么从契约里去掉。

## 十一、两处契约空洞的改写 + 窗口验收（同日再收口）

上一节留的两条，按「改写」处理：都换成**可推、有唯一答案**的那一问。

### FL04 `band` → 先算总量，再折一半

六格光带被删掉了。查下去它比「装饰」还差一层：`pair_rules.gd` 顶上的 `OCCURRENCES` 常量
（`[0,1,1,2,0,2]`，看上去是「每架灯归到哪两次合称」的答案）**从来没有被任何代码读过**，
`kind:"band"` 这个动作在 `scripts/ui/` 里也找不到入口——一整套没写完就没接上的设计。

换成的两步都落在灯下：

| 步骤 | 文案 | 答案 | 怎么推出来 |
|---|---|---|---|
| ① 总量 | 先算总量：三次合称一共多少格？ | 94 | `sum_expected()` = ab+bc+ac |
| ② 一套 | 三次合称里每架灯都被称了两次。一套灯架的总重是： | 47 | `total_expected()` = 总量 ÷ `occurrences()` |

`occurrences()` 是从 `RIGS_OF_PAIR` 这个配对结构里数出来的（数「甲」出现在三对里的次数），
不是写死的 2——原来那句 `(ab+bc+ac)/2` 里的 2 才是写死的。

**这一步顺手避开一个坑**：给 FL04 接 `total` 时用的「新档」标记是 `proof`，
而上一版（本轮之前）**已经发过** `proof`、但那一版还没有 `sum`。
如果继续拿 `proof` 当分界，上一版留下的通关存档会因为「有 proof 却没有 sum」被读成没做完。
所以分界改成了 `sum` 的键有无（`Pair.strict()`），三代存档各按各自当时的判据走：

| 存档 | 有 `proof` | 有 `sum` | 判据 |
|---|---|---|---|
| 更早那一版 | 没有 | 没有 | 三对吻合 + `weighed` 齐（若带该字段） |
| 上一版 | 有 | 没有 | 同上 |
| 现在 | —— | 有 | 上面再加「总量 = 94 且一套 = 47」 |

### FL15 `outcome_count` → 至少要称几次

原来那一问（「一次天平最多有几种结果」，填 3）不但和思考不搭界，**它自己也泄漏**：
盘面上那行说明早就写着「一次天平最多 3 种结果」，玩家等于在抄。

改成「九颗至少要称几次才够？」，答案由 `minimal_weighings()` 推出：
最小的 k 使 `3^k ≥ 颗数`。九颗 → 2；三颗 → 1；一颗 → 0。
提示第 3 档跟着改成只摆前提（「一次称量最多能把几种情况分开？」），第 4 档才报次数。

`required_evidence` 两条相应改写：
FL04「用三条光带标出每架重复计数两次，组成总量47」→「先算三次合称的总量，再折出一套灯架的重」；
FL15「用一次至多3种结果说明一次不能区分9种情况」→「由一次最多分开3种情况推出至少要称两次」。
另外 FL04 的 `hints[2]`（原先直接写着 94 / 47）也一并改掉——那一档现在归 `guide()` 管、本来不会被读到，
但旧宿主 `scripts/main.gd` 仍会按层数念它，留着就是把答案留在数据里。

### 窗口验收：窗口启动即最小化

窗口套件一直是 `FLAG_NO_FOCUS`（不抢焦点），但窗口仍然会出现在屏幕上。现在 `window_focus.gd`
的 `configure()` 顺手把它最小化；`ready()` 在每次投输入前会补做一次——`p8_playtest` 中途会改
`root.size`，那一步可能把窗口还原出来。

这不是靠猜：写了个临时探针（用完即删）实测最小化之后的三件事。

| 要看什么 | 实测 |
|---|---|
| 是否交出焦点 | `focus=false`（最小化前是 `true`——启动瞬间其实抢了一下） |
| 主循环还在推进吗 | 600ms 内 88 帧，正常 |
| 还能截到真实画面吗 | 能。画一块 `d24b3c` 的纯色，最小化后 `force_draw` + `get_texture().get_image()` 逐点取回的还是 `d24b3c` |

第三行是必须查的：所有 `*_playtest.gd` 都用 `capture()` 把截图写进 `docs/playtest/forest-release/`，
如果最小化让帧缓冲变成空图，验收截图就全废了。实测没有。

`ready()` 末尾的断言也从「visible 且 no-focus」改成了「**mode 必须是 MINIMIZED** 且 no-focus」——
断言跟着需求走，不然以后有人把最小化删掉，套件照样是绿的。

### 窗口套件同步到新门禁

改玩法没改窗口套件的话，这次窗口验收会红在四处：`p3_playtest` 的 FL04（少了总量与总折）、
FL05（少了押注），`p6_playtest` 的 FL14（少了判因与代价）、FL15（少了次数）、FL16（少了押注与代价）。
这些以前是「命令驱动」（`scenarios.gd`），这一轮它们走的是**真实鼠标键盘输入**，
所以两边都要改：`scenarios.gd` 已在上一步同步，窗口套件按同样的顺序补上真实点击与输入。

所以「放 572、框从 598 起」看起来还有 2px，实际已经压上了——留余量要按撑大后的高度算。
